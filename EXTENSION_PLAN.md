# Extension Plan

## Goal

Replace `e_agent_tool::extension!` with a module attribute macro that:

- describes an extension and contributes optional system-prompt text;
- discovers the module's tools;
- optionally manages one in-memory state object per session;
- hides extension state and session identity from tool schemas and model-visible arguments.

The first version remains an in-process tool extension system. It does not attempt to reproduce Pi's full extension runtime.

## Proposed API

```rust
#[extension(
    description = "Manage an in-memory task list",
    system_prompt = "Use todo for multi-step work and print the full list after every change."
)]
mod todo {
    #[state]
    #[derive(Default)]
    struct TodoState {
        next_id: u64,
        tasks: Vec<Task>,
    }

    #[tool]
    async fn create_todo(
        #[state] state: &mut TodoState,
        subject: String,
    ) -> Result<String> {
        state.create(subject);
        Ok(state.render())
    }

    #[tool]
    async fn list_todos(
        #[state] state: &TodoState,
    ) -> Result<String> {
        Ok(state.render())
    }
}
```

`description` is required. `system_prompt` is optional and defaults to an empty string. A module may contain zero or one `#[state]` struct.

## State Model

Each stateful extension owns a macro-generated process-local map:

```rust
static __E_AGENT_STATES: OnceLock<DashMap<SessionId, TodoState>> = OnceLock::new();
```

The host owns session identity. Every `Session` receives a process-local `SessionId` generated from an `AtomicU64`. Session IDs are never exposed as model tool parameters.

Before executing Python for a session, `ProgrammaticToolExecutor` sets the current session ID through a hidden function generated by `#[extension]`. The generated tool wrapper reads that ID, gets or creates the corresponding `DashMap` entry with `TodoState::default()`, and passes `&TodoState` or `&mut TodoState` to the user's Rust function.

Properties:

- tools in the same extension and session share one state object;
- different sessions receive different state objects;
- different extensions own separate maps;
- state is lost when the process exits;
- a hidden `__e_agent_drop_session__(session_id)` entry removes one session slot when the host explicitly closes a session.

`DashMap` is internally synchronized rather than lock-free. Its entry guard remains held while a stateful tool future runs. Stateful tools must therefore keep their state section short, must not recursively invoke another stateful tool from the same extension, and should not perform long-running I/O while holding the state reference. This is acceptable for in-memory TODO mutations. Revisit the representation if stateful tools later need long asynchronous work.

## Macro Expansion

### `#[extension]`

The outer macro runs before inner item macros and is responsible for the module as a whole:

1. Parse `description` and optional `system_prompt`.
2. Find tool functions declared directly in the module.
3. Find at most one struct marked `#[state]`.
4. Generate the PyO3 module initializer and cancellation bridge currently produced by `extension!`.
5. For a stateful extension, generate the `DashMap<SessionId, State>`, current-session bridge, and session-drop entry.
6. Export one JSON metadata value named `__e_agent_extension__`.
7. Leave inner `#[tool]` attributes in place to generate each tool's typed wrapper.

The state struct must implement `Default + Send + Sync + 'static`. The generated code should force these bounds so violations produce compile-time errors.

### `#[tool]`

A tool may contain at most one parameter marked `#[state]`:

```rust
#[state] state: &TodoState
#[state] state: &mut TodoState
```

The tool macro must:

1. Verify that the parameter type matches the extension's marked state struct.
2. Exclude the state parameter from the generated `Input` struct.
3. Exclude it from JSON Schema and the Python function signature.
4. Exclude it from model-visible metadata.
5. Generate a wrapper that resolves the current `SessionId`, obtains the `DashMap` entry, and injects the reference when calling the user's function.

The user's Rust function keeps the explicit state parameter. Do not inject a magic local variable into the function body: the explicit parameter preserves type checking, editor support, read/write intent, and understandable diagnostics.

Stateless extensions and stateless tools continue to work without a `#[state]` struct or parameter.

## Metadata

The macro exports metadata through the existing PyO3 boundary:

```json
{
  "name": "todo",
  "description": "Manage an in-memory task list",
  "systemPrompt": "Use todo for multi-step work...",
  "functions": []
}
```

Replace `ToolModule` with extension metadata carrying `description`, `system_prompt`, and tool functions. `ProgrammaticToolExecutor` parses it, keeps load order deterministic, and exposes extension system prompts to `Session::build_system_prompt()`.

## Host Changes

1. Add `SessionId(u64)` and assign one in `Session::new`.
2. Extend the executor call boundary to receive the current `SessionId` without adding it to model arguments.
3. Set and clear the extension's hidden current-session value around Python execution, including error paths.
4. Add an explicit executor operation that calls `__e_agent_drop_session__` on every loaded extension when a session is closed.
5. Keep the existing per-turn cancellation behavior unchanged.

The initial executor currently serializes Python execution, so the hidden current-session slot may be a generated process-global value inside each cdylib. If independent sessions later execute extension code concurrently, replace that bridge with a per-call Python `ContextVar` or equivalent context propagation before enabling such concurrency.

## Validation Rules

- Reject an empty extension description at compile time.
- Reject more than one `#[state]` struct in an extension.
- Reject `#[state]` outside an `#[extension]` module.
- Reject a tool state parameter when its extension has no state struct.
- Reject more than one state parameter in a tool.
- Reject state parameters other than `&State` or `&mut State`.
- Reject duplicate tool function names while loading an extension.
- Reject malformed or missing exported metadata with the module path in the error.
- Keep extension prompt order equal to `E_AGENT_TOOL_PATHS` load order.
- Loading the same module name replaces its prior metadata and module registration.

## Tests

1. Macro test: metadata contains module name, description, optional system prompt, and all direct tools.
2. Macro test: a `#[state]` parameter is absent from input schema and Python signature.
3. Macro compile-fail tests for invalid extension fields and every state validation rule.
4. Loader test: extension metadata round-trips through PyO3.
5. State test: create and list share state within one session.
6. Isolation test: two sessions using one loaded extension cannot observe each other's state.
7. Isolation test: two stateful extensions cannot observe each other's state.
8. Cleanup test: dropping one session removes only that session's state.
9. Loader test: reloading the same module replaces metadata instead of duplicating it.
10. Session test: base prompt, runtime context, and extension prompts are assembled in deterministic order.
11. Workspace test: existing `basic_tools`, `my_ext`, and `web-access` modules load and execute after migration.

## Non-Goals

- Session persistence or branch trees.
- `ToolOutput.details`; model-visible state must be printed by tool code.
- UI/TUI widgets, commands, shortcuts, or render hooks.
- General lifecycle or event hooks.
- Hot reload and extension-local persistent storage.
- Multiple state types in one extension.
- Custom state constructors; state uses `Default`.
- A separate `promptSnippet` / `promptGuidelines` abstraction; `description` and `system_prompt` cover the current need.

## Implementation Order

1. Define `SessionId` and serializable extension metadata.
2. Implement the `#[extension]` module macro and migrate existing stateless extensions.
3. Implement `#[state]` struct discovery and state-parameter filtering in `#[tool]`.
4. Add the generated `DashMap` state store and hidden session bridge.
5. Pass `SessionId` through the host executor and implement cleanup.
6. Aggregate extension system prompts.
7. Add isolation, schema, cleanup, and compile-fail tests.
8. Run `cargo fmt --all`, `cargo check --workspace`, and `cargo test --workspace`.
